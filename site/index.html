How it works

An independent gate around the actions

Your agent proposes a tool call; an adapter asks TARA to authorize it; the policy engine returns allow, deny, or "needs a human." Only an allowed — or human-approved — action gets a single-use grant, and every decision is written to a signed audit log.

Quickstart

Running in a few minutes

Two dependencies, pure Python. Wire the shipped Claude Code adapter, and every tool call routes through TARA.

git clone https://github.com/manju-reddyy/TARA.git
cd TARA
python -m pip install -r requirements.txt   # PyYAML, cryptography

python examples/demo.py       # see allow / deny / approval, live
python tests/test_tara.py     # 213 security tests
python tara/server.py         # the authorization server + approval window

Then point Claude Code's hooks at TARA so every tool call is authorized first:

{
  "hooks": {
    "PreToolUse":  [{ "matcher": "*", "hooks": [{ "type": "command",
        "command": "python /path/to/TARA/tara/hook.py" }] }],
    "PostToolUse": [{ "matcher": "*", "hooks": [{ "type": "command",
        "command": "python /path/to/TARA/tara/hook.py --post" }] }]
  }
}

Any framework

Write your own adapter

The engine authorizes on (tool_name, tool_input) — the agent is just a free-form label, so nothing is tied to one model or vendor. To onboard a framework, translate its tool-call events into three HTTP calls. (MCP, LangGraph, and Microsoft Agent Framework adapters are on the roadmap.)

# 1. Ask TARA to authorize the action the agent proposed
POST /authorize  { "agent": "my-framework", "tool_name": "...", "tool_input": {...},
                   "session_id": "...", "cwd": "...", "task": "..." }
   → { "decision": "allow" }                         # run the tool
   → { "decision": "deny",  "reason": "..." }         # block it
   → { "decision": "pending", "request_id": "..." }   # a human must approve

# 2. For a pending request, wait for the human's biometric approval
POST /wait     { "request_id": "..." }  → { "status": "approved", "grant": "..." }

# 3. Redeem the single-use grant at the moment you run the tool
POST /consume  { "grant": "...", "tool_name": "...", "tool_input": {...} }  → { "ok": true }

Why it's safe

Built to assume the agent is compromised

Most guardrails ask the model that was hijacked to also stop the hijack. TARA puts the authorization boundary around the actions instead.

Fails closed

Unreachable, frozen (kill switch), or any error → the action is denied. Safety never depends on TARA staying up.

The agent's words never authorize

Injected “the user already approved this” is ignored. Approval is an out-of-band human biometric the agent can't see.

Biometric human approval

A fingerprint on a separate device; two different enrolled fingerprints for critical, two-person actions. Iris / ear-placement and a one-time code can layer on as extra checks.

Single-use, action-bound grants

One approval authorizes one execution of one exact action (tool + arguments, bound by hash). Replays are rejected.

Protected resources stay locked

TARA's own keys, audit log, and your credentials are hard-denied — approval can't unlock them.

Tamper-evident audit

Every decision, approval, and execution is appended and Ed25519-signed. The public key is served so anyone can verify the chain.
